## 2 分支结构

```text
main
├─ feature/web-diagnostic-workbench   前端集成线
├─ feature/equipment-database         数据库与后端集成线
├─ feature/equipment-rag              项目负责人维护的 RAG 集成线
└─ feature/diagnosis-agent            Agent 与端到端集成线
```

四条长期分支代表四个技术模块，不代表四名成员。项目负责人同时维护 RAG 和 Agent 两条线。日常开发从长期分支创建 `task/issue-编号-内容`、`fix/issue-编号-内容`、`test/issue-编号-内容` 或 `docs/内容` 短分支。

禁止直接向 `main` 推送。长期功能分支也通过 Pull Request 接收短分支，避免一次提交混入多个无关功能。

## 3 项目负责人职责

### 产品与 Stitch

- 明确目标用户、比赛范围、核心场景和演示故事；
- 用 Stitch 维护设备中心、设备档案、诊断工作台、工单和看板；
- 提供颜色、字体、间距、组件状态、桌面尺寸和异常状态；
- 与前端负责人确认设计可实现性和页面优先级。

### RAG 检索

- 解析 PDF 说明书和维修规范，保留文件、版本、页码和设备型号；
- 实现分块、向量检索、关键词检索和可选 Rerank；
- 返回文档、版本、页码、引用片段和检索分数；
- 建立至少 20 条问题、标准答案、证据位置和评分标准；
- 处理无答案、文档冲突和模型不可用场景。

### Agent 与总集成

- 定义 Agent 工具的名称、参数、返回值、权限、超时和失败回退；
- 区分数据库事实、RAG 证据、模型推断和待人工确认项；
- 维护跨模块接口契约、里程碑和端到端演示流程；
- 审查 PR 的产品一致性、安全边界和比赛要求；
- 负责部署、录屏、架构图、答辩稿和材料一致性。

### 代码边界与首批任务

主目录为 `app/agent/`、`app/rag/`、`app/services/retrieval/`、`evals/` 和 `docs/architecture/`。Agent 不直接执行 SQL，不跳过确认修改设备或工单；RAG 不得静默覆盖数据库关键参数。

首批短分支：

1. `task/issue-3-document-ingestion` 完成 PDF 解析和元数据；
2. `task/issue-3-hybrid-retrieval` 完成混合检索和来源引用；
3. `test/issue-3-rag-evaluation` 建立 20 条评测集；
4. `task/issue-4-agent-tool-contract` 定义 Agent 工具契约；
5. `task/issue-4-human-confirmation` 完成高风险建议和写操作确认；
6. `task/issue-4-e2e-demo` 打通设备查询、文档证据、诊断和工单。

PR 必须证明检索证据可定位、无证据时不编造、工具失败时不伪造结果，写操作经过用户确认和权限校验。

## 7 跨模块接口契约

| 契约 | 提供方 | 使用方 | 合并前确认内容 |
|---|---|---|---|
| OpenAPI 与错误码 | 后端负责人 | 前端和项目负责人 | 路径、字段、分页、权限和错误示例 |
| 设备参数查询工具 | 后端负责人 | Agent | 企业隔离、参数来源和时间戳 |
| 文档检索工具 | 项目负责人 | Agent 和前端 | 文档、版本、页码、片段和分数 |
| Agent 运行事件 | 项目负责人 | 前端和后端 | 步骤状态、工具输入输出、错误和确认 |
| 工单状态机 | 后端负责人 | 前端和 Agent | 可用状态、转换规则和审计字段 |
| Stitch 设计规范 | 项目负责人 | 前端负责人 | 组件、尺寸、状态和响应式规则 |

接口修改必须先更新文档或 OpenAPI，再修改调用方。PR 中说明兼容性和受影响模块。

## 8 Pull Request 工作流

1. 在 Issue 下写清本次子任务和验收标准；
2. 从对应长期功能分支创建短分支；
3. 每次提交只处理一个主题，使用 `feat`、`fix`、`test` 或 `docs` 前缀；
4. 作者同步上游分支并解决冲突后再发 PR；
5. PR 描述包含 Issue、改动、测试、截图或接口示例、风险和回退；
6. 至少一名非作者批准，跨模块改动由受影响模块负责人共同查看；
7. 使用 squash merge，合并后删除短分支；
8. 长期功能分支达到里程碑后，再向 `main` 提交集成 PR。

前端 PR 由项目负责人审查，涉及接口时后端负责人一起审查；后端 PR 由项目负责人审查，涉及页面时前端负责人一起审查；RAG 和 Agent PR 由前端或后端负责人至少一人审查；端到端集成 PR 由三人共同查看。

## 9 Pull Request 完成标准

- 达到 Issue 验收标准；
- 自动测试通过，填写真实测试命令和结果；
- UI 有截图或录屏，API 有请求响应示例，数据库有迁移和回退；
- 文档和示例配置已经更新；
- 不包含密钥、真实企业数据或版权不明文档；
- AI 生成代码已经由作者理解、运行和人工检查；
- 已在集成环境验证，不只在作者电脑上运行。
