# 制造领航 ForgePilot：GitHub 分支协作与详细分工

这份文档用于实际开发协作。成员先认领技术角色，再在固定功能分支上工作；每个可验收的小功能仍应拆成短分支和 Pull Request，避免四个人长期同时修改同一条分支。

## 1. 成员与主责

| 角色 | 当前成员 | 长期分支 | 主 Issue | 最终负责的结果 |
|---|---|---|---|---|
| 产品、Stitch、Agent 与总集成 | 项目负责人 | `feature/diagnosis-agent` | #4 | 产品范围、设计规范、Agent 编排、跨模块集成、部署与答辩 |
| React 前端负责人 | 待三名队员确认 | `feature/web-diagnostic-workbench` | #2 | 可运行 Web 端、组件与页面测试、录屏 |
| 数据库与 FastAPI 后端负责人 | 待三名队员确认 | `feature/equipment-database` | #1 | ER 图、迁移、设备与工单 API、权限及测试 |
| RAG 与检索评测负责人 | 待三名队员确认 | `feature/equipment-rag` | #3 | 文档管线、混合检索、来源引用、评测报告 |

`Fabric-devc` 已加入仓库；`Fabric-creat` 已邀请。两人和第三名队员需要在开工会中分别选择前端、后端或 RAG。不要在角色确认前仅凭账号名猜测分工。

## 2. 分支结构

```text
main
├─ feature/web-diagnostic-workbench   # 前端集成线
├─ feature/equipment-database         # 数据库与后端集成线
├─ feature/equipment-rag              # RAG 集成线
└─ feature/diagnosis-agent            # Agent 与端到端集成线
```

长期功能分支用于保存各主线的集成状态。日常开发推荐从对应长期分支再创建短分支：

```text
feature/equipment-database
└─ task/issue-1-device-schema

feature/web-diagnostic-workbench
└─ task/issue-2-device-list-page
```

短分支命名规则：

- `task/issue-<编号>-<内容>`：普通功能；
- `fix/issue-<编号>-<内容>`：缺陷修复；
- `test/issue-<编号>-<内容>`：独立测试；
- `docs/<内容>`：纯文档。

禁止直接向 `main` 推送。长期功能分支也尽量通过 PR 接收短分支，不把多个互不相关的功能塞进一次提交。

## 3. 项目负责人：产品、Stitch、Agent 与总集成

### 3.1 负责内容

- 用 Stitch 维护设备中心、设备档案、诊断工作台、工单和数据看板；
- 提供颜色、字体、间距、组件状态、桌面尺寸和异常状态说明；
- 定义 Agent 工具协议：工具名、输入、输出、权限、超时和失败回退；
- 维护 OpenAPI、跨模块数据结构和演示流程；
- 审核产品一致性、安全边界、关键数据来源和 PR 证据；
- 负责最终集成、部署、录屏、架构图、答辩稿和比赛材料。

### 3.2 代码边界

- 主目录：`app/agent/`、`app/services/agent/`、`docs/architecture/`；
- 可修改：跨模块契约、配置示例、集成测试；
- 不包办：前端页面、数据库全部 CRUD、RAG 全部实现；
- 不允许：Agent 直接执行 SQL、无确认创建工单、把模型输出当成设备事实。

### 3.3 首批任务

1. `task/issue-4-agent-tool-contract`：提交 Agent 工具契约；
2. `task/issue-4-agent-run-state`：保存运行步骤、工具调用和错误；
3. `task/issue-4-human-confirmation`：实现高风险建议和写操作确认；
4. `task/issue-4-e2e-demo`：打通数据库、RAG、前端和工单演示。

### 3.4 PR 验收

- 能解释每个工具为什么存在及权限范围；
- 工具失败时不伪造结果；
- 事实、推断、引用与待确认项在响应中明确区分；
- 写操作有用户确认、权限校验和审计记录；
- 提供端到端测试或可复现演示步骤。

## 4. React 前端负责人

### 4.1 负责内容

- 建立 React、TypeScript、路由、状态管理和 API Client；
- 把 Stitch 页面转换为可维护组件，不直接提交一次性导出 HTML；
- 完成设备列表、设备档案、诊断工作台、工单和看板；
- 完成加载、空数据、错误、无权限、断网和重试状态；
- 为关键交互编写组件测试或端到端测试；
- 提供桌面端截图、操作录屏和与 Stitch 的差异说明。

### 4.2 代码边界

- 主目录：`frontend/`；
- 与后端只通过 OpenAPI 通信，不直接访问数据库；
- 后端未完成时使用与 OpenAPI 同结构的 Mock；
- 不在浏览器保存模型密钥，不在组件中散落 API 地址。

### 4.3 首批任务

1. `task/issue-2-frontend-foundation`：工程、路由、主题和 API Client；
2. `task/issue-2-device-pages`：设备列表和设备档案；
3. `task/issue-2-diagnosis-workbench`：对话、工具步骤、引用和人工确认；
4. `task/issue-2-work-orders`：工单列表、详情、状态流转和结果回看；
5. `test/issue-2-ui-states`：核心页面状态与响应式测试。

### 4.4 PR 验收

- 关联 #2 或 #4，并附截图或录屏；
- TypeScript 无新增类型错误；
- 覆盖加载、空、错误和权限状态；
- API 类型与 OpenAPI 一致；
- 不把 Mock 结果伪装成真实后端结果。

## 5. 数据库与 FastAPI 后端负责人

### 5.1 负责内容

- 设计企业、用户、工厂、产线、设备、部件、参数、故障、工单、备件和审计模型；
- 使用 PostgreSQL 与迁移工具管理结构变更；
- 实现登录、角色权限和企业数据隔离；
- 实现设备、参数、历史故障和工单 API；
- 保证外键、唯一约束、状态约束、事务和幂等；
- 提供虚构种子数据、OpenAPI、回退方案和自动测试。

### 5.2 代码边界

- 主目录：`app/api/`、`app/models/`、`app/schemas/`、`app/repositories/`、`migrations/`；
- 数据库保存结构化事实，不存模型猜测为权威参数；
- RAG 文档正文和向量可独立保存，但必须通过设备型号或文档 ID 关联；
- 写接口必须做权限、校验和审计。

### 5.3 首批任务

1. `task/issue-1-er-model`：ER 图、字段字典和模型评审；
2. `task/issue-1-postgres-migrations`：PostgreSQL、迁移和种子数据；
3. `task/issue-1-device-api`：设备与参数 CRUD；
4. `task/issue-1-tenant-rbac`：企业隔离和角色权限；
5. `task/issue-4-work-order-api`：工单状态机、审计和历史回写。

### 5.4 PR 验收

- 关联 #1 或 #4；
- 迁移可从空库执行，也有明确回退方式；
- OpenAPI 示例与真实响应一致；
- 覆盖越权、重复提交、非法状态流转和事务失败；

## 6. RAG 与检索评测负责人

### 6.1 负责内容

- 解析 PDF 说明书和维修规范，保留文件、版本、页码和设备型号；
- 设计分块、向量索引、关键词索引和可选 Rerank；
- 返回引用片段、页码、文档版本和检索分数；
- 建立至少 20 条问题、答案、证据位置和评分标准；
- 处理无答案、文档冲突、旧版本文档和模型不可用；
- 记录检索命中率、引用准确率、响应时间和调用成本。

### 6.2 代码边界

- 主目录：`app/rag/`、`app/services/retrieval/`、`data/demo-documents/`、`evals/`；
- 文档内容只能作为证据来源，不能静默覆盖数据库关键参数；
- 没有证据时必须返回“未找到可靠依据”；
- 演示文档必须虚构、公开授权或已脱敏。

### 6.3 首批任务

1. `task/issue-3-document-ingestion`：PDF 解析、页码和版本元数据；
2. `task/issue-3-hybrid-retrieval`：向量与关键词混合检索；
3. `task/issue-3-citations`：标准化引用响应；
4. `test/issue-3-rag-evaluation`：20 条评测集和自动评分；
5. `task/issue-4-retrieval-tool`：封装为 Agent 可调用工具。

### 6.4 PR 验收

- 关联 #3 或 #4；
- 查询结果能定位到文件、版本和页码；
- 提供无答案与冲突文档测试；
- 提供评测数据和本次指标变化；
- 不提交版权不明或包含敏感信息的文档。

## 7. 跨模块接口契约

| 契约 | 提供方 | 使用方 | 合并前必须确认 |
|---|---|---|---|
| OpenAPI 与错误码 | 后端 | 前端、Agent | 路径、字段、分页、权限、错误示例 |
| 设备参数查询工具 | 后端 | Agent | 企业隔离、参数来源、时间戳 |
| 文档检索工具 | RAG | Agent、前端 | 文档、版本、页码、片段、分数 |
| Agent 运行事件 | 项目负责人 | 前端、后端 | 步骤状态、工具输入输出、错误与确认 |
| 工单状态机 | 后端 | 前端、Agent | 可用状态、转换规则、审计字段 |
| Stitch 设计规范 | 项目负责人 | 前端 | 组件、尺寸、状态与响应式规则 |

任何契约修改必须先更新文档或 OpenAPI，再修改调用方。禁止在同一 PR 中偷偷改变接口而不说明兼容性。

## 8. PR 工作流

1. 在 GitHub Issue 下写清本次子任务和验收标准；
2. 从对应长期功能分支创建短分支；
3. 每次提交只处理一个主题，使用 `feat:`、`fix:`、`test:`、`docs:`；
4. 作者先同步上游分支并解决冲突，再发起 PR；
5. PR 描述必须包含 Issue、改动、测试、截图或接口示例、风险和回退；
6. 至少一名非作者批准，跨模块改动由受影响模块负责人共同查看；
7. 使用 squash merge；合并后删除短分支；
8. 长期功能分支达到里程碑后，再向 `main` 发起集成 PR。

推荐审查关系：

- 前端 PR：项目负责人审查；涉及接口时后端负责人补充审查；
- 后端 PR：项目负责人审查；涉及检索结构时 RAG 负责人补充审查；
- RAG PR：项目负责人审查；涉及设备模型时后端负责人补充审查；
- Agent 或端到端 PR：四人查看，至少一名非作者批准。

## 9. PR 完成标准

- 达到 Issue 验收标准；
- 自动测试通过，PR 中粘贴真实测试命令和结果；
- UI 有截图或录屏，API 有请求响应示例，数据库有迁移与回退；
- 文档和示例配置已更新；
- 没有密钥、真实企业数据或版权不明文档；
- AI 生成代码已经由作者理解、运行和人工检查；
- 已在集成环境验证，不只是在作者电脑上运行。
