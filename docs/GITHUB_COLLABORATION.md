## 2 分支结构

```text
main
├─ feature/product-web-experience   任务包 A
├─ feature/data-service-platform    任务包 B
└─ feature/ai-agent-rag             任务包 C
```

长期分支保存每个任务包的集成状态。日常开发从长期分支再创建短分支：

- `task/issue-<编号>-<内容>` 用于普通功能；
- `fix/issue-<编号>-<内容>` 用于缺陷修复；
- `test/issue-<编号>-<内容>` 用于独立测试；
- `docs/<内容>` 用于纯文档。

任何人都不能直接向 `main` 推送。短分支通过 Pull Request 合入任务包长期分支；任务包达到里程碑后，再向 `main` 提交集成 Pull Request。

## 8 Pull Request 工作流

1. 在 Issue 下写清本次子任务和验收标准；
2. 从所选任务包的长期分支创建短分支；
3. 每次提交只处理一个主题，使用 `feat`、`fix`、`test` 或 `docs` 前缀；
4. 作者同步上游分支并解决冲突后再发 PR；
5. PR 描述包含 Issue、改动、测试、截图或接口示例、风险和回退；
6. 至少一名非作者批准，跨任务包改动由受影响负责人共同查看；
7. 使用 squash merge，合并后删除短分支；
8. 长期分支达到里程碑后，再向 `main` 提交集成 PR。

审查关系：A 的 PR 由 B 或 C 至少一人审查；B 的 PR 由 A 或 C 至少一人审查；C 的 PR 由 A 或 B 至少一人审查；端到端集成 PR 由三人共同查看。

## 9 Pull Request 完成标准

- 达到 Issue 验收标准；
- 自动测试通过，填写真实测试命令和结果；
- UI 有截图或录屏，API 有请求响应示例，数据库有迁移和回退；
- 文档和示例配置已经更新；
- 不包含密钥、真实企业数据或版权不明文档；
- AI 生成代码已经由作者理解、运行和人工检查；
- 已在集成环境验证，不只在作者电脑上运行。
