摘要

ForgePilot 把制造企业设备维护中分散的“设备档案、说明书知识、现场现象、维修任务、操作记录”收敛到一个 Web 工作台，用检索增强生成（RAG）与真实大模型给出**有证据、可核对、需人工确认**的诊断建议，再把建议转化为可跟踪的维修工单和审计记录。

1. 项目背景与需求

1.1 问题

信息分散设备运行数据在监控系统，说明书在共享盘或个人电脑，维修任务在表格或聊天群里，三者无法互相对照。
经验依赖现场判断依赖老师傅经验，新人难以快速定位“应该先查什么”，也难以说明依据。
过程不可追溯诊断结论、谁确认、何时建单、改了哪些字段，缺少统一记录。
AI 不可信直接让大模型给结论，容易出现无依据回答、引用错文档、把推断当事实。

1.2 目标

  • 用一个工作台串起：设备查询 → 证据检索 → AI 辅助诊断 → 人工确认 → 生成工单 → 维修验收 → 审计追踪。
  • AI 的每一个判断都能回到说明书原文；不能回到原文的内容必须明确标注为推断或待验证。
  • 模型只提建议，保存诊断、确认风险、生成工单都由人触发，并且幂等、可审计。
  • 首条验收路线固定为演示设备 AC-07 螺杆空气压缩机，不使用未标明的静态数据伪装真实接口。

1.3 非目标

  • 不做设备远程控制，不自动执行停机、启机或参数下发。
  • 不在没有授权数据时宣称企业真实诊断能力；当前全部为虚构演示数据。
  • 不把系统做成通用聊天机器人，而是围绕设备维护流程的受控工作流。
对应比赛评分：AI 深度、创新、前端工程、实用性、用户体验、社会价值与商业潜力。

2.2 关键设计

  • 身份由业务服务签发 Bearer Token；知识服务每次请求回查业务服务确认身份，不信任客户端伪造组织头。
  • 前端有 mock | api 两种数据模式；API 模式请求失败会明确报错，不回退成演示数据。
  • 知识服务保持单实例 + 持久化卷；多实例前必须先改造知识库存储。

3.1 核心对象

Devicedevice_id、model、plant、health、status首条演示设备 AC-07
DeviceParametername、value、unit、threshold设备专属测点，不同设备指标不同

3.2 权限与隔离

  • 导航按岗位显示；维修人员只能处理本人告警/工单，主管负责验收与取消。
  • 所有查询带组织条件；跨组织设备返回 403，不泄露是否存在。
  • 人员停用前必须选择未完成工单接收人，转派写入审计。
  • 知识文档上传、删除限制管理岗位，并校验组织归属。

3.3 幂等与事务

人工确认生成工单时，以诊断 ID 作为幂等键；重复确认返回同一张工单。保存诊断、确认、建单在同一事务边界内完成，失败整体回滚，避免“诊断已保存但工单只建了一半”。

实现位置：services/business/app/api、app/security.py；迁移见 services/business/alembic。

4. AI 方案：RAG 与证据诊断

1 解析说明书文本抽取与分块
2 检索BM25 + 设备型号/组织过滤
3 组装问题 + 设备事实 + 证据片段
4 生成DeepSeek 结构化输出
5 校验引用回查 + 降级

4.1 为什么先检索再生成

设备维护是强证据场景。模型参数里的“常识”不能替代本厂说明书。ForgePilot 先检索与当前设备型号匹配的说明书片段，把原文和来源一并交给模型，要求它只基于给定证据回答；检索不到足够证据时直接返回“证据不足”，而不是编一个答案。

4.2 证据与引用

  • 每条证据带文档标题、页码/片段、设备型号、组织、相似度分数。
  • 模型输出必须引用证据 ID；服务端逐条校验引用是否存在于本次检索结果。
  • 存在无效引用时整体降级：替换原回答与摘要，标记 status=degraded，前端不允许保存为正式诊断。
  • 设备型号不一致时拒绝检索（model_mismatch），避免 AC-07 查到 CNC 手册。

4.3 结构化诊断

字段含义页面呈现
statements.fact文档直接支持的内容文档陈述
statements.inference模型基于证据的推断模型推断
statements.pending仍需现场确认的内容待验证项
conflicts资料之间或资料与现场描述冲突冲突提示
verificationSuggestions建议补采的测点/工况证据补采清单
model / tokens模型名与输入/输出/合计 Token结果顶部与诊断记录

5. 人工在环与受控 Agent

5.1 人机分工

模型负责检索证据、归纳文档陈述、提出推断、列出待验证项、给出补采建议。
人负责判断现场风险等级、决定是否采纳、保存诊断、确认生成工单、完成维修验收。

5.2 为什么不让模型直接建单

  • 诊断错误会带来停机、备件和安全风险，必须有人承担确认责任。
  • 模型无法知道现场是否已断电、是否具备备件、是否影响生产计划。
  • 人工确认后建单，才能把“谁确认、依据哪些证据、何时建单”写进审计。

5.3 受控只读 Agent

POST /api/v1/agent/assist 执行固定白名单工具：设备查询 → 同设备历史工单 → 证据诊断。每一步返回状态（ok / unavailable）和数量，前端逐步展示；工具名、状态、数量写入业务服务审计，不发送提问原文或模型回答。Agent 不修改设备、不创建工单，也不能绕过人工确认。

5.4 可观测性

诊断响应返回模型 provider、model、输入/输出/合计 Token；诊断保存时记录模型来源，便于在工单与审计中回溯“这条建议由哪个模型、消耗多少 Token 生成”。

{
  "status": "ok",
  "is_mock": false,
  "model": "deepseek-flash",
  "input_tokens": 890,
  "output_tokens": 1014,
  "total_tokens": 1904,
  "sources": [ ... 3 条证据 ... ],
  "statements": [fact, inference, pending]
}

6. 核心功能与界面

6.1 维护总览与设备中心

总览按当前组织实时聚合；不同设备使用不同指标，切换设备后测点、趋势、告警和资料摘要同步更新。设备导入支持 CSV 模板与扫码内容录入，扫描依赖浏览器 BarcodeDetector，同时提供手动粘贴。

6.2 告警与工单

告警区分待确认、处理中、已关闭；工单支持设备与负责人指派、优先级、计划时间、步骤勾选、提交验收、退回、完成和取消。草稿可删除，正式工单取消保留痕迹。

7. 诊断闭环实拍

7.1 一次完整操作

  1. 从告警或设备页进入诊断工作台，目标设备自动带入 AC-07。
  2. 输入现场描述：“运行一段时间后越来越烫，排气温度接近预警，应该先检查什么？”
  3. 系统检索说明书证据，调用 DeepSeek，返回事实 / 推断 / 待验证三类内容。
  4. 右侧证据阅读器逐条核对原文；冲突与补采建议单独展示。
  5. 人工选择风险等级 → 保存诊断 → 确认生成工单，编号贯穿后续。
  6. 在工单页指派、排期、推进状态；在审计页按编号追溯诊断与建单。

截图为线上演示环境实拍，模型信息、Token 用量和证据数量均来自真实接口响应。

8. 知识与审计

8.1 知识管理

  • 支持虚构说明书上传，服务端解析后返回文本预览；管理岗位可删除误上传文档。
  • 文档按组织隔离，检索时同时按设备型号过滤，避免跨设备引用。
  • 引用保留文档标题、片段、页码与相似度，前端可点击定位原文。

8.2 审计追踪

  • 登录、告警处理、工单创建/编辑/验收/取消、诊断保存/确认、人员改岗与转派均写审计。
  • 记录操作人、时间、对象类型与 ID、动作、前后字段变化。
  • Agent 工具调用单独记录工具名、状态和数量，不记录提问原文与模型回答。

9. 关键实现

9.1 前端适配层

所有请求集中在 frontend/src/services/api.js：统一注入 Bearer Token、组织标识、错误码映射与超时；mock 与 api 两种模式共用页面组件，避免两套 UI。API 模式失败只提示错误，不回退演示数据。

9.2 身份与权限

业务服务用随机 AUTH_SECRET 签发 Token，解析后得到组织、用户、角色；知识服务通过 C_IDENTITY_API_BASE_URL 回查 /api/v1/auth/me，逐请求透传身份。生产环境缺少身份服务配置时拒绝启动，避免“裸奔”。

9.3 诊断保存与建单

只有 is_mock=false 且证据校验通过、状态为 ok 的诊断才允许保存；确认接口以诊断 ID 幂等，重复请求返回同一工单；建单与诊断状态更新在同一事务内，异常回滚。

9.5 关键取舍

  • 选择 BM25 而非向量库：演示资料规模小、可解释、零额外基础设施；接口预留替换空间。
  • 选择单进程 JSON 知识库：先保证可运行与可复现，明确标注多实例前必须迁移。
  • 选择“证据不足就降级”：宁可少答，不把无依据内容包装成诊断。

11. 安全、数据与合规

11.1 数据边界

  • 设备、告警、工单、说明书均为虚构演示数据，未使用未授权企业原始资料。
  • 仓库只提交 .env.example；模型密钥、数据库口令、登录令牌不进入 Git。
  • 企业数据接入前需确认授权主体、脱敏样例、使用范围（比赛/课程/GitHub/作品集）、保密与删除要求。

11.2 应用安全

  • 身份由服务端解析，不信任客户端伪造组织/用户头。
  • 模型密钥只在知识服务环境变量；前端仅配置公开 API 地址。
  • CORS 限定自定义域名；生产环境要求 HTTPS、独立密钥与受控来源。
  • Agent 白名单只读工具，落库与建单必须人工触发。

11.3 备案与页面标识

站点已完成 ICP 备案并在页脚展示备案号；公安联网备案按流程办理。演示页明确标注“虚构演示数据 / 请勿录入真实敏感信息”。

11.4 当前限制

  • 云端容器使用 SQLite 与 JSON 知识库，重新部署或实例重启会恢复种子数据。
  • 演示账号公开，仅用于评审与体验；不承载真实生产数据。
  • 尚未接入企业真实传感器与阈值规则，不能宣称自动判定设备超限。

12. 创新点与展望

12.1 创新点

证据优先的诊断 UI把“文档陈述 / 模型推断 / 待验证项”分栏呈现，AI 输出从一段话变成可核对的清单。
引用校验与整体降级无效引用不是悄悄删掉，而是整体降级并禁止保存，避免“看起来完整”的错误诊断。
人工在环的建单闭环模型建议不直接变成任务，风险分级与建单由人确认，并用幂等键保证重复操作安全。
可观测与可追溯模型名、Token 用量、证据数量进入诊断记录与审计，能回答“这条建议怎么来的”。

12.2 展望

  • 接入企业授权的设备手册与维修记录，建立按设备型号的阈值与工况规则。
  • 知识库迁移到向量检索 + 持久化数据库，支持多实例与增量更新。
  • 增加设备二维码扫码定位、移动端维修验收与离线草稿。
  • 在受控范围内扩展 Agent 工具（备件库存、排班、工单优先级建议），继续坚持只读与人工确认。

12.3 结语

ForgePilot 不追求“让 AI 替人修设备”，而是让维护人员在每一步都能看到依据、做出判断、留下记录。对一个面向中小制造企业的作品来说，可信、可追溯、可落地，比模型参数更重要。
